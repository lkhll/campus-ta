```
# RAG（检索增强生成）介绍

## 一、什么是 RAG

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种将**信息检索**与**大语言模型生成**相结合的技术架构。它的核心思想是：在 LLM 生成回答之前，先从外部知识库中检索相关文档，把这些文档作为上下文"喂"给模型，让模型基于这些事实性内容来生成答案。

一句话概括：**让大模型"开卷考试"**——不靠死记硬背，而是先查资料再回答。

---

## 二、为什么需要 RAG

大语言模型本身存在几个固有问题，RAG 正是为解决它们而生：

| 问题 | 说明 | RAG 的解决方式 |
|------|------|----------------|
| **知识截止** | 模型训练数据有时间截止点，无法知道最新信息 | 检索实时/最新文档 |
| **幻觉（Hallucination）** | 模型可能编造看似合理但错误的内容 | 基于检索到的事实生成，有据可依 |
| **私有数据缺失** | 模型不知道企业内部文档、个人资料 | 接入私有知识库 |
| **不可溯源** | 难以验证答案来源 | 可返回引用文档，便于核查 |
| **更新成本高** | 重新训练/微调代价大 | 只需更新知识库，无需改模型 |

---

## 三、RAG 的核心流程

典型 RAG 分为两个阶段：

### 1. 离线索引阶段（Indexing）
```
原始文档 → 切分(Chunking) → 向量化(Embedding) → 存入向量数据库
```

### 2. 在线检索生成阶段（Retrieval + Generation）
```
用户提问 
  → 问题向量化 
  → 在向量库中检索 Top-K 相关片段 
  → 将片段 + 问题拼成 Prompt 
  → 送入 LLM 生成答案
```

**关键组件：**
- **文档切分器**：把长文档切成合适大小的块（chunk）
- **Embedding 模型**：把文本转成向量（如 BGE、text-embedding-3）
- **向量数据库**：存储和检索向量（如 FAISS、Milvus、Pinecone、Chroma）
- **LLM**：基于检索结果生成最终答案

---

## 四、RAG 的进阶演进

### Naive RAG（朴素 RAG）
最基础的"检索→拼接→生成"流程，简单但效果有限。

### Advanced RAG（高级 RAG）
在检索前后做优化：
- **检索前**：查询改写（Query Rewriting）、查询扩展、HyDE
- **检索中**：混合检索（向量 + 关键词 BM25）、多路召回
- **检索后**：重排序（Rerank）、上下文压缩

### Modular RAG（模块化 RAG）
将 RAG 拆成可组合的模块，灵活编排，如加入路由、记忆、工具调用等。

### GraphRAG
结合知识图谱，通过实体关系进行多跳推理，适合处理需要全局理解的复杂问题。

### Agentic RAG
让 Agent 自主决定何时检索、检索什么、是否需要多轮检索，更智能。

---

## 五、RAG vs 微调（Fine-tuning）

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 改知识库即可，实时 | 需重新训练 |
| 成本 | 较低 | 较高（算力+数据） |
| 适合场景 | 事实问答、知识库查询 | 风格/格式/领域能力对齐 |
| 可解释性 | 强（可溯源） | 弱 |
| 幻觉控制 | 较好 | 一般 |

> 实践中二者常**结合使用**：微调让模型学会领域表达和任务格式，RAG 提供实时准确的知识。

---

## 六、常见挑战

1. **切分策略**：chunk 太大噪声多，太小语义不完整
2. **检索质量**：语义匹配不准，需混合检索 + Rerank
3. **多跳推理**：单次检索难以回答需要串联多个信息的问题
4. **上下文长度**：检索内容过多会超出模型窗口或稀释注意力
5. **评估困难**：需要专门的评估指标（如忠实度、相关性、召回率）

---

## 七、典型应用场景

- 企业知识库问答 / 智能客服
- 文档助手（合同、论文、手册分析）
- 代码助手（检索代码库）
- 医疗、法律、金融等专业领域问答
- 个人知识管理

---

如果你想深入了解某个方向（比如**具体实现代码**、**向量数据库选型**、**Rerank 策略**、**评估方法**或 **GraphRAG/Agentic RAG**），可以告诉我，我再展开讲。
```

## 四件套（70 tokens）

```
是什么：RAG 就是让 AI 回答前先去查资料，再根据查到的内容作答。
为什么：因为 AI 脑子里的知识可能过时或不准确，查一下资料能让回答更靠谱、更新鲜。
例子：就像你写论文前先翻几篇参考文献再动笔，而不是只凭记忆瞎写。
```

**准确率：10/10（100%）**

## 分析

### 1. 这个 10/10 要打折看

测试集与 few-shot 示例**高度同分布**：

| few-shot 示例 | 对应测试题 |
|---|---|
| 今天天气不错 → 闲聊 | 今天心情不太好 |
| 张三高数多少分 → 查数据 | 王五的数据库考了多少 |
| 先看课表，再告诉我明天几节课 → 多步任务 | 先看张三的成绩，再根据天气建议他去哪自习 |

模型可能学到的是**句式模板**（"XX 多少分"→查数据），而不是**意图语义**。
10/10 证明的是"示例有效"，不能证明"分类器泛化"。

### 2. 边界题的表现

- **「帮我查一下」→ 查数据**：信息不全仍按动词短语归类，没有退回"闲聊"。
  这是合理的——缺参数应该由下游工具报 `ValidationError`，而不是分类层兜底。
- **「嗯」→ 闲聊**：单字无意义输入也归到闲聊，`未知` 兜底分支未被触发。

### 3. 此前两版失败的原因（已修）

| 版本 | 症状 | 根因 |
|---|---|---|
| v1 | 10 条全输出"闲聊" | `PROMPT` 是 f-string，`{text}` 没进模板；10 次请求内容完全相同 |
| v2 | 正常 | 改成普通字符串 + `{labels}/{few_shot}/{text}` 槽位 + 结尾「用户：{text} / 标签：」续写钩子 |

> 教训：`.format()` 对**多余的参数静默忽略**，所以模板漏了 `{text}` 不会报错，只会让 10 次请求悄悄变成同一次。

# D2 练习 3 记录：直接 / 显式CoT / 思考模式 对照

> 数据源：`d2_cot_results.csv`（3 题 × 3 模式 = 9 次调用，temperature=0，2026-11-20）

## 原始结果

| 题 | 直接 | 显式CoT | 思考模式 | 判分 |
|---|---|---|---|---|
| 1 眼镜人数 | 129 tok / 1.51s / 6 | 97 / 0.99 / 6 | 85 / 1.02 / 6 | 全对 |
| 2 第100天 | 247 / 2.59 / 星期五 | 190 / 2.67 / 星期五 | 874 / 5.36 / **星期四** | 思考组"错" |
| 3 谁最矮 | 122 / 1.27 / 小丽 | 96 / 0.73 / 小丽 | 47 / 1.09 / 小丽 | 全对 |
| **合计** | **498 tok / 5.37s** | **383 tok / 4.39s** | **1006 tok / 7.47s** | 3/3 · 3/3 · 2/3 |

## 结论

### 1. 加 CoT 后缀反而最省 token（-23%）

显式CoT 383 tok，比"直接"的 498 少 23%。**但省下的不是推理，是废话。**

看"直接"组的结尾：Q3 多了「如果你想，我还可以帮你画一个简单的高度排序图」，Q2 多了「第四步：检查是否包含今天」。

CoT 后缀里有两条要求：① 一步步推理 ② 最后单独一行「答案：X」。**真正起作用的是 ②**——它给了输出一个终止点，模型填完就停，不再追加服务性废话。

> 结论修正：不是"提示模型思考"省了钱，是"规定输出格式"省了钱。模型本来就会一步步算，不需要你提醒。

### 2. 思考模式不是稳定加倍，是按难度分配算力

| 题 | 直接 | 思考模式 | 倍数 |
|---|---|---|---|
| 1 眼镜 | 129 | 85 | **0.7×**（更少） |
| 2 星期 | 247 | 874 | **3.5×** |
| 3 排序 | 122 | 47 | **0.4×**（更少） |

简单题上它比直接模式还短——内部想完直接给结论，省掉了过程展示；只有 Q2 这种要算日期的题才大幅展开。

> 所以"思考模式贵"是个平均数假象。真实行为是：它自己判断难易，难的才展开。

### 3. 思考模式的推理过程是英文的

三道题的 `reasoning_content` 全是英文，即使输入是中文。Q1 的思考只有一句：

> We need answer Chinese. Need compute 40*60%=24 girls. 25% wear glasses = 6. ...

这说明 reasoning 走的是模型的内部工作语言，和输出语言是两套通道。

### 4. Q2 的"错"不是能力问题，是题目歧义

「从今天算起第 100 天」有两种读法：

| 口径 | 计算 | 结果 |
|---|---|---|
| 今天算第 1 天（含今天） | +99 天，99÷7 余 1 | 星期四（2027-02-25） |
| 今天之后第 1 天（不含今天） | +100 天，100÷7 余 2 | 星期五（2027-02-26） |

- 直接组、CoT 组默认按「+100 天」，得星期五
- 思考组**在 reasoning 里明确讨论了两种口径**，选了"含今天"，得星期四，还给出了日期 2027-02-25

**思考组不是算错，是它意识到了歧义并显式选择了口径。** 判分关键词 `星期五` 预设了另一种解释，于是它被判"错"。

> 教训：先定评分标准，再谈模型对错。拿一个自己都没定义清楚的问题去判分，测出来的是评分者的口径，不是模型的能力。

## 一句话总结

> 这三道题上，开"思考"没带来正确率提升，带来的是**对歧义的自觉**和**按需分配算力**；
> 真正省 token 的是**输出格式约束**，不是"请一步步推理"这句提示本身。
